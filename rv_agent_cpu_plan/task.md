# RVA-01 · 带 I/D Cache 的 RV64IM 五级流水线 CPU

**设计需求**：单发射、顺序提交的 64-bit RV64IM CPU。必须明确分开 IF/ID、ID/EX、EX/MEM、MEM/WB 四组级间寄存器，不允许用单指令多周期控制器冒充五级流水线。支持 RV64I 整数算术、逻辑、移位、分支、跳转、字节/半字/字/双字访存、LUI/AUIPC（普通 `fence` 不在范围，`fence.i` 属于 Zifencei，需实现）；支持 RV64M 的 `mul/mulh/mulhsu/mulhu/div/divu/rem/remu` 及 `*w` 形式；支持 Zicsr 六种 CSR 操作、MRET、ECALL 和 CLINT 定时器中断。无 F/D/A/C 扩展，无 MMU，无 S-mode/U-mode，无外部异步中断（只有 CLINT MTIP），只有 M-mode。`x0` 恒为 0；JALR 应按 ISA 清目标 bit0（注意：参考 RTL 未显式清零，现有 87 例也未覆盖奇数目标，Agent 实现仍应实现该语义）。取指按 4 字节对齐（无 C 扩展）；数据访存支持 `unalign-cpu-tests` 中的字节/半字/字非对齐访问（由 byte lane/写掩码完成），但不要求非对齐宽访存产生精确异常。

本任务的能力基线是 `projects/cpu_axi_diff/vsrc`（本仓库 `bb69f74`）。该参考设计在本仓库的 difftest 流程中通过 `bin/non-output/cpu-tests` 33/33、`bin/non-output/riscv-tests` 50/50，并通过 `bin/custom-output` 的 yield/time/interrupt/rt-thread 四例，共 **87/87**；另外可选回归 `cpu-tests-fencei` 36/36、`cpu-tests-ysyx4` 35/35。任务要求描述该参考设计的可观察能力；参考设计不具备的功能不作为验收项。公开骨架 `public/cpu_axi_diff/` 即从该设计抽取，验收以同一套 87 例为准（见“公开 RTL 骨架与 Agent 出题说明”）。

## 设计出发点与评测准则

**本测试旨在用来评测上市面上流行的前沿模型，是否可以利用自身agent能力，在给定的任务中完成芯片研发中的真实工作，在相同的题目下比较各个模型的功能完成情况、以及芯片的PPA指标。开发的agent需要在2小时内交付一套完整的RISC-V CPU。此任务不仅仅是编写RTL代码，还需要agent理解长语义上下文的芯片Spec，理解需求并调用合适的工具完成设计及迭代验证的工作。**

**以下从****设计出发点、任务边界、评测指标、评分流程、评测原则**五个层面展开。本文既作为被测 Agent 的任务说明书，也作为评审 Agent 的评分依据；所有指标都要求可由脚本或证据复核，避免主观印象分。

**本轮题面提供****完整验证环境**：验证平台、87 条公开用例、DiffTest/黄金模型、运行脚本和日志格式均由题面给出，Agent 不需要自建验证环境。基线 RTL 有两种模式：**缺陷修复/补全模式**（题面提供含缺陷或待补全的 RTL）和**从零实现模式**（题面提供空骨架）；无论哪种，Agent 的核心工作都是理解规格与微架构、完成实现或修复、用提供的环境跑通 87 条用例、完成回归，并给出可被复核的 PPA 自评。原任务描述中的“自建验证环境”环节由题面提供的完整验证环境替代；两种模式共用同一评分框架，仅在 F2/F3 的权重细节上按题面微调。

#### 1. 设计出发点：为什么用“五级流水线 RISC-V CPU”作为 Agent 试金石

1. **复杂度处于可交付的甜点区。** 五级流水线（IF/ID/EX/MEM/WB）既包含真实 CPU 的主要工程矛盾——数据冒险、控制冒险、结构冒险、流水线冲刷、存储器接口、复位与异常——又不至于像乱序执行、多核或 Cache 一致性那样超出 2 小时的可交付边界。它足以区分“会写代码”与“会做芯片”。
2. **把 2 小时集中在最能区分能力的环节。** 题面提供完整验证环境，Agent 不需要搭建 TB、黄金模型和回归脚本；有限时间被集中到规格理解、微架构理解、实现/修复、缺陷定位、回归验证和自评上。缺陷修复模式更接近真实团队中 senior 工程师的 debug 工作；从零实现模式则同时考察架构到 RTL 的落地能力。两种模式都能在 2 小时内拉开差距。
3. **正确性有客观锚点。** RISC-V 指令语义公开、编码确定，题面提供的 ISS/DiffTest 可以作为黄金模型，用 87 条公开用例、隐藏随机/定向用例和逐指令提交比对做自动化判定，避免“看起来能跑”。
4. **轻量 PPA 仍然能区分架构选择。** 不能跑完整综合/STA/功耗流程时，用“平均 IPC + 寄存器/状态 bit 数 + 活动率代理”仍能区分前递与停顿、分支解析位置、流水级寄存器数量、寄存器堆实现等关键取舍。它不等同于签核级 PPA，但足以比较架构效率，且测量成本低、可复现。
5. **工具链轻量、结果可复现。** 仿真器、DiffTest、日志解析和寄存器统计脚本都可以在容器内固定版本运行；相同输入应得到相同日志和统计结果。EDA 面积/功耗报告作为可选证据，不作为所有模型的必需项。
6. **难度可分档。** 基础档为 RV64I + 87 条公开用例（开发集，本题基线为 RV64IM）；评分档为隐藏冒险/边界用例 + 更多随机种子；挑战档加入二次故障注入或 ECO 规格变更。同一评分框架可覆盖不同能力层级的模型，避免“全过”或“全挂”的 ceiling/floor 效应。

| **P2 面积** | **15**   | **寄存器/状态 bit 数（触发器 + 推断存储器/寄存器堆；外部存储器不计）的归一化得分；数量越少越好；若题面统一启用综合流程，可用 cell area 替代状态 bit 数；五级结构不合规时 P2 = 0** | **elaboration/Yosys**`stat`报告、模块拆分 |
| **P3 功耗** | **10**   | **优先使用固定条件下的 EDA 功耗报告；否则用 VCD 统计每周期寄存器翻转 bit 数作为动态功耗代理，静态功耗用状态 bit 数代理；VCD 不可用时直接用状态 bit 数作为粗代理；越低越好**       | **功耗报告或 VCD/翻转统计、代理公式**     |

**轻量 PPA 口径：**

* **为什么简化**：2 小时预算和部分评测环境无法稳定跑通综合/STA/功耗，完整签核级 PPA 既不可比也不公平。本测试改用客观、低成本的代理指标，重点是区分架构效率，而不是替代 signoff。
* **测量主体**：由评审 Agent 用统一脚本在交付的 `vsrc` 上测量，不采信 Agent 自报数字；Agent 自评只用于交叉检查和“自评可信度”评估。
* **性能**：从 87 条用例日志读取 `instret` 与 `cycles`，计算每条用例 IPC，再对所有通过用例做算术平均；不要用墙钟时间、仿真时间或代码行数代替。IPC 以 testbench 独立记录的周期数与退休指令数为准；若使用 CPU 内部计数器，必须与 testbench 交叉校验，不一致时以 testbench 为准。未通过用例不计入平均，但公开通过率 < 80% 时性能样本偏差过大，P1 直接为 0。题面分类表（ALU/分支/load-use/存储）的 IPC 作为辅助分析，不改变主分。
* **面积**：统计所有时序状态 bit，包括通用寄存器堆、流水线寄存器、CSR/计数器、状态机、推断的存储器；外部 DRAM/存储器模型不计。若把寄存器藏进推断 RAM，仍计入状态 bit，防止“面积优化”造假。统计优先用 Yosys `stat`，不可用时用题面提供的 Verilator/elaboration 统计脚本；所有模型同一口径。若所有模型都能跑同一综合流程，题面可统一改用 cell area；否则仍以状态 bit 数为准。
* **功耗**：优先用题面固定工艺角/电压/温度/活动率下的 EDA 报告；不可用时，用仿真 VCD 统计每周期寄存器翻转 bit 数作为动态功耗代理，静态功耗用状态 bit 数代理；若 VCD 也没有，直接用状态 bit 数作为静态+动态粗代理（不再乘 IPC），并在报告中明确标注为 proxy。若无法保证所有模型都能跑同一 EDA 流程，则以统一代理为准，EDA 报告只作参考证据。
* **归一化公式**：题面优先给定参考实现的 `IPC_ref`、`Area_ref`、`Power_ref` 与底线/优秀线；没有参考值时，用同批最优值作满分线（`*_ref`）、最差值作 0 分线（`*_floor`/`*_ceiling`），中位数只作描述统计，并在报告中注明。建议按分段线性计算：`P1 = 20 × clamp((IPC − IPC_floor)/(IPC_ref − IPC_floor), 0, 1)`；`P2 = 15 × clamp((Area_ceiling − Area)/(Area_ceiling − Area_ref), 0, 1)`；`P3 = 10 × clamp((Power_ceiling − Power)/(Power_ceiling − Power_ref), 0, 1)`。性能越高越好，面积/功耗越低越好；超过参考线即满分，不额外加分。
* **架构合规门槛**：P2/P3 只在五级流水线结构完整、未删除必需流水级/寄存器/前递逻辑的前提下计分；若通过合并流水级、删除状态或把本应内部的功能移出 `vsrc` 来降低面积/功耗，F5 记 0，P2/P3 记 0。
* **自评门槛**：Agent 必须使用题面统一口径提交自评 PPA（公式、数据、命令、单位）。若发现明显漏洞——无报告却声称 EDA 结果、状态 bit 数与复测相差 > 20% 且无法解释、用墙钟时间冒充 IPC、单位/数量级错误、只挑快用例、自评与交付数据矛盾——PPA 项直接记 0（按题面约定）。

##### 3.4 资格门槛、封顶与扣分

* **功能门槛**：F < 25（功能不足 50%）时 P = 0；25 ≤ F < 40 时 P 封顶 22.5；F ≥ 40 才按实际 PPA 计分。
* **公开通过率门槛**：87 条公开用例通过率 < 80% 时 F1 = 0，且 P1 = 0（性能样本偏差过大）；< 60% 时视为未形成可用 CPU，P = 0，总分封顶 70。
* **隐藏类别门槛**：任一隐藏类别通过率 < 60%，该类别计 0；两类及以上 < 60%，F2 总分封顶 12.5（50%）。
* **Elaboration/lint 失败**：F4 = 0，P = 0，总分封顶 60。
* **缺交必交物**：每缺一项扣 3 分；缺 87 条日志/IPC 时 F3 = 0、P1 = 0；缺自评 PPA 或评分卡时 PPA 记 0（自评是必交件）。
* **自评 PPA 明显漏洞**：见 3.2 口径，PPA 项直接记 0，并在报告中记录证据。
* **回归退化**：最终版本每退化一个此前通过的公开用例扣 0.5 分，最多扣 5 分；中间日志显示通过、最终版本失败且无合理解释的，按退化处理。
* **架构取巧**：通过删除流水级、合并寄存器、删除前递/状态、把本应在 CPU 内的功能移出 `vsrc` 或藏进外部存储器模型来降低面积/功耗的，F5 = 0，P2 = P3 = 0。
* **超时**：>120 分钟总分记 0（题面硬性规定）。
* **篡改测试/黄金模型、伪造日志或 PPA、硬编码答案、获取题目未授权的设计/测试资源或使用外部 IP**：取消资格，总分 0；日志与评审复跑结果不一致且无合理解释的，按伪造处理。
* **能力与结果不匹配**：公开测试接近满分而隐藏测试显著偏低（差距 > 25 个百分点），标记过拟合/硬编码嫌疑，F2 按隐藏实际成绩计，PPA 封顶 50%。

##### 3.5 区分项与同分裁决（不计入 100 分）

* **可选 EDA 证据**：若环境支持，提交综合面积/功耗报告、关键路径或资源利用率分析，作为“物理实现意识”的加分证据；不作为必需项，也不能替代统一代理口径。
* **扩展能力**：M 扩展、Zicsr/异常与中断、I/D Cache、分支预测（BHT/BTB）、调试接口；仅在题面允许的基线范围内计分。
* **质量证据**：需求追踪矩阵、调试报告（现象→假设→实验→根因→修复→回归）、补充定向用例、测试覆盖/风险分析。
* **自评准确度**：主要比较自评 IPC/状态 bit/功耗代理与复测的偏差；≤10% 记为“可信”，10%–20% 记为“部分可信”，>20% 且无合理解释或方法错误按 3.2 处理。总分自评偏保守或偏激进本身不扣分。
* **同分排序**：隐藏测试通过率 → 平均 IPC → 状态 bit 数（低者优）→ 功耗代理（低者优）→ 交付完整度 → 自评准确度。

##### 3.6 能力画像（不计分，供分析）

**评审 Agent 另按 0–5 分给出八维雷达图：****规格理解、架构理解、Debug 定位、验证环境使用、轻量 PPA 估算、工具与自动化、工程交付、自评与自主**。画像不进入总分，用于解释排名、识别单项能力突出但总分相近的模型，以及为后续题目设计提供依据。

#### 4. 评分流程：自动化优先，评审 Agent 复核

1. **环境与仓库校验**：检查 `vsrc` 是否存在、测试目录/黄金模型/评分脚本的哈希是否不变、`vsrc` 外的基线/骨架文件是否被改动、工具版本和网络隔离是否符合题面；记录实际用时。
2. **静态检查**：运行 elaboration/lint，检查五级流水线结构、接口/复位/x0、文件布局、禁止构造（latch、多驱动、仿真专用语法、绝对路径、硬编码结果）。
3. **功能评测**：先在 clean 环境跑 87 条公开用例，逐条记录 PASS/FAIL、周期数、退休指令数；再跑隐藏集，按 3.1.1 的类别统计通过率，记录首个分歧点、分歧指令和现场状态。
4. **轻量 PPA 测量**：用统一脚本统计状态 bit 数、从评审复跑日志计算平均 IPC、按 3.2 口径计算功耗代理；若题面提供参考值，按参考值归一化；EDA 报告仅作可选证据。
5. **复现评测**：在干净容器中按运行说明/README 用交付的 `vsrc` 和题面脚本重跑，比较 87 条结果、IPC、状态 bit 数和 PPA 代理；不能复现的数据一律作废。
6. **自评审计**：把 Agent 提交的自评 PPA/评分卡与独立复测对比；检查公式、单位、数据来源和命令；判定“可信 / 部分可信 / 明显漏洞”，后者按约定将 PPA 记 0。
7. **评审 Agent 复核**：使用版本化 rubric 对 F3/F5、自评可信度等定性项逐项打分，每个分数必须引用具体文件、日志或报告位置；不得凭整体印象给分。
8. **汇总与归档**：输出总分、分项分、雷达图、证据索引、违规记录和排名；保留原始产物不少于一个评测周期。

**评审 Agent 的一致性要求：**

* **对模型名称和来源做匿名化，交付件随机排序；评审 Agent 不应是被评模型本身；**
* **以单评审 Agent 为主；前 3 名、临界名次和自评异常样本由人工抽检复核；条件允许时对前 3 名双评，分歧超过 10% 时人工仲裁；**
* **用已知分数的校准样本定期校验评审 Agent；**
* **评审 Agent 应亲自重跑脚本，不能只读 README 或模型自述；**
* **评分理由必须可定位到证据，避免“完成度高”“代码优雅”等无依据表述。**

#### 5. 评测原则

1. **同题同权同预算**：题面、基线、验证环境、工具、硬件、时间、token 与工具调用上限完全一致；模型版本与调用日期固定并记录。
2. **Debug 结果与过程并重**：通过率是硬结果，但根因定位、最小修复、回归无退化、日志可复现同样计入 F3；不接受“碰巧改对”的无证据通过。
3. **证据链原则**：每个结论都要有命令、日志、报告、波形或 diff 支撑；声明与证据不一致时，以证据为准并扣分。
4. **可复现原则**：87 条用例、IPC 和 PPA 代理都能由评审 Agent 在 clean 环境复跑；相同输入重复运行应得到相同结果，随机测试使用固定 seed 集合并记录。
5. **隐藏集完备性**：公开 87 条用于开发，隐藏集按 3.1.1 的覆盖矩阵补齐；隐藏集在指令组合、程序长度、冒险模式上应与公开集有结构性差异，防止过拟合。
6. **反 reward hacking**：重点检测改测试/黄金模型、伪造日志或 PPA、硬编码答案、选择性汇报、删除流水级/寄存器骗面积、把本应内部的状态藏进外部存储器模型等行为；一经确认，取消资格或对应项归零。
7. **自评仅作参考**：Agent 自评用于交叉检查和可信度评估，排名以评审 Agent 独立复测为准；自评明显漏洞按约定将 PPA 记 0。
8. **PPA 代理口径透明**：同一批模型必须使用同一测量模式（EDA / VCD / 状态 bit 代理）；不允许用不同口径互相比较；报告中必须写明公式和限制。
9. **多维不折叠**：总分用于排名，雷达图与分项分用于解释；不允许用一个综合分掩盖功能、Debug、面积、功耗中的单项崩塌。
10. **难度分档、避免天花板与地板**：87 条公开用例保证强模型可完成、弱模型有部分分；隐藏类别与可选加试用于区分头部模型；题面应先做小样本校准，确保分数分布有区分度。
11. **可重复实验**：条件允许时每个模型独立运行 3 次，取中位数并报告方差；至少记录单次运行的随机性来源（seed、工具版本、模型温度），单次结果不足以支撑强排名结论。
12. **评审一致性与匿名化**：rubric 版本化、评分可追溯、单评审 + 人工抽检；评审 Agent 不得因文风、篇幅或模型品牌产生偏好。
13. **安全与合规**：禁止使用未经许可的外部 IP、闭源参考设计或题目未授权的联网资源；仅允许获取题面指定的固定版本依赖；引用公开资料需在运行说明/README 中声明来源与许可证。

```systemverilog
  input  logic         io_memAXI_0_ar_ready,
  output logic         io_memAXI_0_ar_valid,
  output logic [63:0]  io_memAXI_0_ar_bits_addr,
  output logic [2:0]   io_memAXI_0_ar_bits_prot,
  output logic [3:0]   io_memAXI_0_ar_bits_id,
  output logic         io_memAXI_0_ar_bits_user,
  output logic [7:0]   io_memAXI_0_ar_bits_len,
  output logic [2:0]   io_memAXI_0_ar_bits_size,
  output logic [1:0]   io_memAXI_0_ar_bits_burst,
  output logic         io_memAXI_0_ar_bits_lock,
  output logic [3:0]   io_memAXI_0_ar_bits_cache,
  output logic [3:0]   io_memAXI_0_ar_bits_qos,

  // AXI4 master：r
  output logic         io_memAXI_0_r_ready,
  input  logic         io_memAXI_0_r_valid,
  input  logic [1:0]   io_memAXI_0_r_bits_resp,
  input  logic [63:0]  io_memAXI_0_r_bits_data [3:0],
  input  logic         io_memAXI_0_r_bits_last,
  input  logic [3:0]   io_memAXI_0_r_bits_id,
  input  logic         io_memAXI_0_r_bits_user
);
```

接口要点：

- `clock` 为 CPU 时钟，正常状态只在上升沿更新。`reset` 为高有效复位；复位保持期间冲刷流水线和 AXI 在途/有效状态，释放后从 `0x8000_0000` 取指。框架在启动时把 `reset` 拉高 10 个周期，随后释放。
- AXI 数据位宽 64，地址位宽 64，ID 4 bit，USER 1 bit。`w_bits_data`/`r_bits_data` 是 4 个 64-bit lane 的 unpacked array，只有 lane 0 被使用；参考实现只连接 lane 0，未驱动 lane 1–3，建议实现中显式置 0。参考实现的 cache line 为 128 bit，因此一次读/写突发为 `len=1` 的两拍、`size=3`（8 byte/beat）、`burst=INCR`；其他合法 AXI4 突发也允许，只要 CPU 自己能正确使用。
- `io_uart_out_valid/io_uart_out_ch` 用于自定义打印指令；`io_uart_in_*` 在本任务中不使用，`io_uart_in_valid` 应驱动 0（参考实现未显式驱动，建议 Agent 显式置 0），`io_uart_in_ch` 可以忽略。
- `io_logCtrl_*` 与 `io_perfInfo_*` 是框架输入，DUT 可以完全忽略。

## 存储器与地址映射

- 测试镜像从 `0x8000_0000` 起加载；仿真器的可访问 DRAM 为 256 MiB（`0x8000_0000`–`0x8FFF_FFFF`，见 `EMU_RAM_SIZE`）。框架通过 AXI 访问该空间；difftest 的 DRAMsim3 后端会把 AXI 地址减去 `0x8000_0000` 后访问 DRAM，因此 CPU 必须发出带 `0x8000_0000` 基址的地址。
- CLINT 位于 CPU 内部，地址范围 `0x0200_0000`–`0x0200_FFFF`，不产生 AXI 事务：
  - `mtime`：`0x0200_BFF8`，可读可写；在 `mtime < mtimecmp` 时每个 `clock` 自增 1，达到/超过 `mtimecmp` 后保持（参考实现用 MTIP 门控自增）。
  - `mtimecmp`：`0x0200_4000`，可读可写，复位值 0。
  - 当 `mtime >= mtimecmp` 时内部 MTIP 有效；复位时两者均为 0，因此 MTIP 初始有效，软件需先写 `mtimecmp > 0` 才能清除。CLINT 范围内其他地址读 0、写忽略。
- DUT 不得硬编码某个测试的 PC、测试名或终止地址来跳过执行。

## 指令与自定义约定

- RV64I：整数算术/逻辑/移位、`slt/sltu` 及其立即数形式、`lui/auipc`、六种分支、`jal/jalr`、`lb/lbu/lh/lhu/lw/lwu/ld`、`sb/sh/sw/sd`；`addiw/slliw/srliw/sraiw` 等 RV64 字操作。普通 `fence` 不实现；`fence.i` 见下条。
- RV64M：`mul/mulh/mulhsu/mulhu/div/divu/rem/remu` 以及 `mulw/divw/divuw/remw/remuw`。
- 取指按 4 字节对齐（无 C 扩展）。数据访存通过 byte lane、写掩码和读数据截取/符号扩展支持 `unalign-cpu-tests` 中的字节/半字/字非对齐访问；不要求非对齐宽访问产生精确异常。
- `0x0000006b` 是 ysyx/oscpu 测试约定的“终止指令”：程序在 `a0` 中放 0 表示通过，非 0 表示失败；DUT 必须让它正常流到退休观察点并产生 `DifftestTrapEvent`，而不是把它实现成非法指令。
- `0x0000007b` 是自定义打印指令：退休时把 `a0[7:0]` 输出到 `io_uart_out_ch`，`io_uart_out_valid` 拉高一个周期。
- `fence.i`（Zifencei，opcode `0001111`、func3=`001`）已实现：退休时清理 D-cache 并 invalidate I-cache；`bin/non-output/cpu-tests-fencei` 36/36 通过。普通 `fence`（func3=`000`）不实现，按 NOP 处理。

## 异常与 CSR

参考设计只实现 M-mode 的有限异常/中断集合；本任务按该可观察行为验收：

- ECALL（`0x00000073`）：精确异常，`mcause = 11`，`mepc = faulting PC`，跳转 `mtvec`。faulting 指令不写回寄存器或内存，年轻指令全部冲刷。
- 定时器中断：当 `mstatus.MIE=1`、`mie[7]=1` 且 CLINT `mtime >= mtimecmp` 时，在当前指令完成后进入中断；`mcause = 0x8000_0000_0000_0007`，`mepc = 被中断指令的 PC`，跳转 `mtvec`。中断周期内 `DifftestInstrCommit.valid` 必须为 0。
- MRET（`0x30200073`）：`PC <- mepc`；`mstatus.MIE <- MPIE`，`MPIE <- 1`，`MPP <- 0`（与参考设计一致）。
- 异常/中断入口的 `mstatus` 更新：`MPIE <- MIE`，`MIE <- 0`，`MPP <- 3`；`mstatus` 其他位保持参考实现的读写行为。
- 非法指令与 EBREAK 不产生异常：参考解码器未匹配的 opcode 按 NOP 处理，EBREAK 按普通 SYSTEM 指令译码但不触发 trap。取指/访存非对齐异常也不实现。这些均不在本任务验收范围内；不要为它们编造与参考不一致的 trap 行为。

CSR 地址与行为（参考设计）：


| CSR        | 地址    | 行为                                                             |
| ---------- | ------- | ---------------------------------------------------------------- |
| `mstatus`  | `0x300` | 可读写；MIE bit3、MPIE bit7、MPP bits12:11 参与异常/MRET；复位 0 |
| `mie`      | `0x304` | 可读写；bit7 为 MTIE                                             |
| `mtvec`    | `0x305` | 可读写；direct 模式，跳转目标为写入值                            |
| `mscratch` | `0x340` | 可读写                                                           |
| `mepc`     | `0x341` | 可读写；异常/中断时写入 faulting PC                              |
| `mcause`   | `0x342` | 可读写；异常/中断时写入 cause                                    |
| `mip`      | `0x344` | 可读写；参考实现`mip[7]` 读 0，MTIP 由内部比较直接送入中断逻辑   |
| `mcycle`   | `0xB00` | 每个`clock` 自增 1；可读写                                       |

支持 `csrrw/csrrs/csrrc` 及三种立即数形式。参考实现不额外抑制 `csrrs/csrrc` 在 rs1=`x0` 或立即数源为 0 时的写操作，而是按普通 CSR 写处理；未列出的 CSR 读 0、写忽略（参考实现不产生非法指令异常）。

## 提交观察口（difftest 挂钩）

本任务不使用 T09 的 `commit_*` 端口，而是使用 oscpu-framework 自带的 XiangShan difftest DPI 模块。DUT 必须在 `SimTop` 内部实例化以下模块（模块定义由 `libraries/difftest/src/test/vsrc/common/difftest.v` 提供，签名固定）：

- `DifftestInstrCommit`：每条正常退休指令产生一个周期的 `valid`；`pc[63:0]`、`instr[31:0]`、`wen`、`wdest[7:0]`、`wdata[63:0]` 必须与架构退休一致；错误路径/被冲刷指令不得产生 `valid`；同一条指令不得重复提交。`skip` 用于告知参考模型跳过不比较的指令：参考实现在 `0x7b` UART 指令、`mcycle` CSR 指令、CLINT 访存指令上置 `skip`。
- `DifftestArchIntRegState`：提交时给出 32 个 GPR 的架构值。
- `DifftestTrapEvent`：`0x6b` 终止指令退休时给出 `valid`，`code = a0[2:0]`，`pc` 为终止指令 PC，`cycleCnt/instrCnt` 为计数。
- `DifftestCSRState`：给出 `mstatus/mepc/mtvec/mcause/mie/mscratch/mcycle` 等架构状态；`priviledgeMode = 3`（M-mode）；未实现的 `s*`/`satp`/`mip` 可为 0。
- `DifftestArchEvent`：中断时给出 `intrNO = mcause`；普通情况 `intrNO = 0`。
- `DifftestArchFpRegState`：无浮点，32 个 `fpr_*` 置 0。

这些观察钩子只用于验收，**不得成为执行功能的输入**。DUT 不得修改 `libraries/difftest` 子模块；框架在编译时会把 `difftest.v` 一起编译。

## 流水线、缓存与资源边界

- 五级流水线：IF、ID、EX、MEM、WB，四组级间寄存器必须实际存在。实现必要的旁路（EX/MEM、MEM/WB、WB→ID）、load-use 停顿、分支/跳转冲刷和数据端等待停顿。
- 无分支预测器；分支/JAL/JALR 在 EX 解析并冲刷年轻指令。乘除法允许使用多周期乘法器/除法器，但必须按顺序提交，不能在结果未就绪时提前提交。
- 独立的 I-cache 与 D-cache，位于 CPU 核与 AXI 之间：
  - 4-way set-associative，128 组，16-byte line，容量 8 KiB（与 `projects/cpu_axi_diff` 及公开骨架一致）；
  - I-cache 缺失时通过 AXI 读入整条 line；
  - D-cache 采用 write-back + write-allocate，store hit 置 dirty，替换时写回整条 line；
  - cache 行为对 ISA 和 difftest 必须透明。
- 寄存器文件 32×64 bit；程序/数据存储器在核外；无 MMU、无 cache 一致性协议、无多核。
- 本任务不设 T09 的 `n+4` 取指到退休硬门禁：参考设计包含 cache miss、AXI 等待和多周期除法，固定延时公式不适用。功能与提交顺序由 difftest 逐条比对；P 组（流水线/缓存/总线）为后续补充的专项检查。
